The self-hosting guide

A little common ground.
On your own laptop.

Run Common for a solo walkthrough, or let one laptop host a shared canvas for colleagues on your LAN or VPN. Keep the application server with your team.

✦

No Netlify account or Postgres needed. The standalone app uses Bun and local files. Team screen sharing adds a trusted HTTPS address through Caddy. The app still has some external defaults, described below.

1. Start on your laptop

Install Bun 1.4.3 and Git. Get read access to the repository, or ask your administrator for a source archive. This repository is currently private; a public app link does not grant source access. The commands below work in macOS/Linux terminals and Windows PowerShell.

git clone https://github.com/alexwelcing/common-workspace.git
cd common-workspace
bun install --frozen-lockfile
cp .env.example .env

If you use a source archive, open a terminal in its extracted project folder instead. In .env, set these two values, leaving the other optional settings as needed:

HOST=127.0.0.1
PORT=3001

Build the standalone frontend, then start its local application server:

bun run build:local
bun run start

Open http://localhost:3001 on this laptop. Use the personal canvas for a solo walkthrough, notes, agent tools, or recording. Browsers treat localhost as a secure context, so Share a window can open the normal capture picker here.

Use build:local for this setup. It builds the WASM/frontend with the standalone WebSocket transport, including when your shell previously selected Netlify polling. The resulting app serves its API, canvas, and session connections from this Bun server; it makes no Netlify runtime API calls and needs no Netlify login.

2. Give the team one HTTPS address

Choose one laptop to host the session. All teammates use that same server; running separate copies on their laptops does not join or federate the canvases.

  1. Keep the Bun server above running. Install the free, open-source Caddy server on the host laptop.
  2. Find the host's LAN or VPN IP address that every participant can reach, such as 192.168.1.50. This example uses an IP directly and needs no DNS setup.
  3. Open public/self-hosting/Caddyfile from the source, or download the Caddyfile. Change its first site address from https://localhost:8443 to your address, for example https://192.168.1.50:8443.
  4. Leave its internal TLS, trust settings, and reverse proxy to 127.0.0.1:3001 intact. Open a second terminal in the same project folder, then run:
caddy run --config public/self-hosting/Caddyfile --adapter caddyfile

If you downloaded the file somewhere else, use that file's path after --config instead.

The example handles HTTPS and WebSocket upgrades and preserves the request host. Bun remains available only on loopback; teammates connect to Caddy on TCP port 8443. Keep Caddy's local administration endpoint on its default loopback address; do not publish port 2019.

Complete the certificate trust step below, then everyone, including the host, opens the same HTTPS address before creating the session. Create a room there and distribute its invite link and password separately.

A link beginning with localhost points to the person opening it, not your hosting laptop. Browser storage also belongs to each origin: http://localhost:3001 and https://192.168.1.50:8443 have separate saved identities and personal canvases. Start at the shared HTTPS address to get the correct invite link.

Keep both terminals running and the host laptop awake. If its IP changes, update Caddy's site address and have everyone use the new origin; existing browser session storage does not move with it.

3. Trust the same local certificate authority

The example uses Caddy's internal certificate authority (CA), rather than requesting a public certificate. Its skip_install_trust setting leaves device trust to your organization. HTTPS must be trusted on every participating device, including the host, before browser screen capture will work reliably.

While Caddy is running, open another terminal on the host laptop and run this command. It reads Caddy's local administration API and saves only the public root certificate to common-local-root.crt in the current directory:

bun -e "const response = await fetch('http://localhost:2019/pki/ca/local'); if (response.ok === false) throw new Error('CA export failed'); await Bun.write('common-local-root.crt', (await response.json()).root_certificate);"

Distribute common-local-root.crt through your organization's approved trust process. Install that same CA in the trust store used by each browser or device; some browsers use a separate store. Your IT team can use managed certificate deployment or its standard device instructions. This includes the hosting laptop: the example does not automatically install trust there.

Share the public root certificate only. Never distribute root.key, other private keys, or Caddy's full data directory. Trusting a CA is a device-level change; use your organization's process and verify that browsers show a trusted connection. Do not work around certificate warnings.

If your organization already has a trusted internal HTTPS proxy or certificate system, it can replace this Caddy setup. Preserve the incoming Host header, forward WebSocket upgrades on /ws, and proxy the app and /api to the same Bun server. See Caddy's official documentation for local HTTPS, the CA export API, and manual trust installation.

To use an organization-issued certificate with the supplied Caddyfile, replace tls internal with the line below. Set the site's address to a hostname or IP covered by that certificate, and make sure every device can resolve and reach it. Keep the private key on the host.

tls /absolute/path/to/server-chain.pem /absolute/path/to/server-key.pem

Where the data lives

Standalone hosting, using new peer-canvas rooms
ContentLocation & lifetime
Room access & chatThe host's data/rooms.json contains room metadata and names, password hashes, token hashes, and recent chat. Restrict access to that file. DATA_FILE can select another writable location.
Shared canvas & imagesNew rooms keep their Yjs canvas and embedded images in participants' browser memory and synchronize between peers. The host server stores no canvas snapshot. Export anything you want to keep before the last copy closes. The personal canvas saves on that browser's device.
Shared windowsVideo travels over WebRTC between peers, with TURN relaying only if configured. The application server does not store the video.
Recordings & snapshotsRecordings remain local browser blobs until downloaded; reloading or closing the tab loses them. Downloads live wherever that user's browser saves files. Recordings are not uploaded or synchronized.

The standalone server's rooms have a default seven-day lifetime. Access tokens last 24 hours and are renewed when their browser reconnects. Explicitly leaving revokes that token; ending the room denies further access. Save needed exports and recordings before leaving.

Common's room creator is the host. This version has password-based rooms and open room creation for visitors who can reach it; it does not add enterprise SSO, administrator-only room creation, or host-account recovery. Use it on a trusted network appropriate to that access model.

Local hosting, with a few external defaults

This setup removes Netlify and Postgres from the runtime. It is not a turnkey offline or air-gapped edition. Source/dependency installation needs access to its repositories, and the canvas app has these defaults:

  • Fonts: the app requests DM Sans from Google Fonts. Self-hosting fonts, or removing that request, needs a source change. This guide itself uses system fonts and loads no external scripts or fonts.
  • STUN: Google and Cloudflare STUN servers help browsers discover reachable network addresses. They receive connection metadata and do not relay the screen video. There is currently no configuration switch to disable the default STUN servers; an organization-only setup needs a source change.
  • Diagrams: Mermaid renders locally. PlantUML rendering sends the full diagram source to plantuml.com after consent. A diagram's shared externalConsent can permit its rendering in other participants' browsers too; do not add confidential source expecting a separate consent prompt on every device.

For restricted networks, your team may need its own STUN/TURN infrastructure and corresponding configuration or source changes. The existing TURN_URLS plus TURN_SECRET settings, or dedicated TURN_USERNAME/TURN_CREDENTIAL, can point at an organization relay. Keep those credentials in the host's environment, not frontend code.

One HTTPS endpoint gets people into the room; canvas and video also need working peer connections. Wi-Fi client isolation, VPN routing, NAT, or firewall policy can block them. Browser WASM does not bypass those network boundaries. There is no fixed room admission cap, but device memory, the full replicated canvas, host signaling work, and presenter upload still limit practical room size.

A few things to check

The page opens, but screen sharing is unavailable

Remote devices need a trusted https:// origin. Plain http://192.168… is not equivalent to localhost. Finish certificate trust, then check browser/operating-system capture permissions and choose the window with the native picker. An organization's browser policy may also restrict capture.

A colleague cannot open the invite link

Check that it uses the host's reachable LAN/VPN IP, not localhost. Keep Bun and Caddy running, prevent laptop sleep, and allow the team's access to TCP port 8443 in the host firewall. Confirm that devices can reach each other on the chosen LAN or VPN.

Rooms open, but the canvas or video never connects

HTTPS room admission can work while peer traffic is blocked. Check VPN routes, Wi-Fi client isolation, peer/UDP firewall rules, and whether your network requires an organization TURN relay. For remote video, use Watch window on its tile; a paused view does not receive live frames.

The local app tries to use polling routes or gets API errors

Rebuild with bun run build:local, restart the Bun process, and reload the page. A frontend built for Netlify polling is not the standalone WebSocket frontend. Confirm that you are using the new local build rather than an older deployed tab.

The room rejects an origin or the WebSocket fails

Use the supplied Caddy reverse proxy with its host-preserving upstream, and have everyone use one common HTTPS origin. A replacement proxy must preserve Host and WebSocket upgrades. ALLOWED_ORIGINS can allow a deliberate additional origin; it does not repair a proxy that sends requests to the wrong server.

The host restarts, and a room or canvas looks different

Room metadata and recent chat use the host's data file, but new shared canvas content lives in browser memory. Keep a browser holding the live document or export what you need. Switching IP, protocol, or port also switches browser origin and its saved identity. An expired token requires joining again with the password.
