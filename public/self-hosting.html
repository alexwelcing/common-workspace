The self-hosting guide

A little common ground.
On your own laptop.

Run Common for a solo walkthrough, or let one laptop host a shared canvas for colleagues on your LAN or VPN. Keep the application server with your team.

✦

No Netlify account or Postgres needed. The local launcher uses Bun, bundled fonts, and a private network profile. Team screen sharing adds a trusted HTTPS address through Caddy. Browsers connect directly by default; no relay service or cloud account is required.

1. Start on your laptop

Install Bun 1.4.3 and Git. Get read access to the repository and the v1.1.0 release, or ask your administrator for a source archive. This repository is currently private; a public app link does not grant source access. The examples use macOS/Linux terminal or Windows PowerShell syntax; the launcher has been exercised on Linux, with native certificate/process behavior on other systems still needing a device check.

git clone https://github.com/alexwelcing/common-workspace.git
cd common-workspace
bun install --frozen-lockfile
bun run doctor
bun run local

For a source archive, open a terminal in its extracted project folder instead. The launcher builds the app and starts its server on loopback at http://localhost:3001. It defaults to the private network profile: no public STUN or external PlantUML renderer unless you configure one.

Open http://localhost:3001 on this laptop. Use the personal canvas for a solo walkthrough, notes, agent tools, or recording. Browsers treat localhost as a secure context, so Share a window can open the normal capture picker here.

bun run doctor checks your Bun version, selected profile, ports, origins, and certificate files without printing secrets. Use bun run doctor --https to include optional Caddy prerequisites, or bun run doctor --json for machine-readable results. After a successful build, bun run local --no-build reuses it.

One frontend build, two hosting choices. The app reads /api/config when it starts. Your Bun server selects WebSocket sessions; the optional Netlify server selects polling. Moving the same built frontend between them needs no transport-specific rebuild or Netlify login for local use.

Prefer to build and start the server yourself?

Copy the environment example and build the app:

cp .env.example .env
bun run build:local

In .env, set these values before running bun run start:

HOST=127.0.0.1
PORT=3001
COMMON_NETWORK_PROFILE=private

build:local remains a compatibility build command; runtime configuration selects transport and network policy. Bare bun run start uses your environment rather than the launcher's private default.

2. Give the team one HTTPS address

Choose one laptop to host the session. Everyone uses that server; running separate copies on their laptops does not join or federate the canvases.

  1. Install the free, open-source Caddy server on the host laptop. Stop the earlier launcher before restarting it with HTTPS.
  2. Find the host's LAN or VPN IP address that everyone can reach, such as 192.168.1.50. An IP address needs no DNS setup.
  3. Start the launcher with that stable address:
bun run local --https --origin https://192.168.1.50:8443

Replace the example IP with your host's address. For HTTPS on the host alone, bun run local --https uses https://localhost:8443. The launcher writes data/local/Caddyfile, keeps Caddy's CA storage under data/local/caddy, and copies its public root certificate to common-local-root.crt in the project folder.

Caddy handles HTTPS, WebSocket upgrades, and the original request host. Bun stays on loopback; teammates connect to TCP port 8443. The generated configuration disables Caddy's administration endpoint. PORT changes the Bun port, COMMON_HTTPS_PORT changes the default HTTPS port, and CADDY_BIN selects an installed Caddy binary. Set COMMON_LOCAL_ORIGIN in your environment to reuse the same address in the launcher and doctor; --origin overrides it.

Complete certificate trust below, then everyone, including the host, opens the same HTTPS address before creating the session. Create a room there and distribute its invite link and password separately.

A link beginning with localhost points to the person opening it, not your hosting laptop. Browser storage belongs to each origin: http://localhost:3001 and https://192.168.1.50:8443 have separate saved identities and personal canvases. Start at the shared HTTPS address to get the correct invite link.

Keep the launcher running and the host laptop awake. If its IP changes, restart with the new --origin and have everyone use it; saved browser identity does not move with it.

Use an existing HTTPS proxy or manual Caddy setup

An organization-issued certificate or internal proxy can replace the launcher's Caddy setup. Run Bun with HOST=127.0.0.1 on the same laptop. The supplied manual Caddyfile uses internal TLS; change its https://localhost:8443 site address to the shared LAN/VPN address, then run it in a second terminal:

caddy run --config public/self-hosting/Caddyfile --adapter caddyfile

A downloaded file may have a different path. Any replacement proxy must preserve Host, forward WebSocket upgrades on /ws, and send both the app and /api to the same Bun server. If your manual Caddy setup enables its administration endpoint, keep it on loopback and do not publish port 2019.

3. Trust the same local certificate authority

The launcher uses Caddy's internal certificate authority (CA), rather than requesting a public certificate. Its skip_install_trust setting leaves device trust to your organization. HTTPS must be trusted on every participating device, including the host, before browser capture will work reliably.

Distribute the exported common-local-root.crt through your organization's approved trust process. Install that same CA in the trust store used by each browser or device; some browsers use a separate store. Your IT team can use managed certificate deployment or its standard device instructions. The launcher does not automatically install trust on the host either.

Share the public root certificate only. Never distribute root.key, other private keys, or Caddy's data directory. Trusting a CA is a device-level change; use your organization's process and verify that browsers show a trusted connection. Do not work around certificate warnings.

Export the public root from a manual Caddy setup

If you started Caddy yourself, run this in another terminal on that host. It reads the local administration API and saves only the public root certificate:

bun -e "const response = await fetch('http://localhost:2019/pki/ca/local'); if (response.ok === false) throw new Error('CA export failed'); await Bun.write('common-local-root.crt', (await response.json()).root_certificate);"

For an organization-issued certificate, replace tls internal in the manual Caddyfile with:

tls /absolute/path/to/server-chain.pem /absolute/path/to/server-key.pem

Use a site address covered by that certificate and reachable by every device. Keep the private key on the host. Caddy's documentation explains local HTTPS, the CA export API, and manual trust installation.

Start with a plan, then make room for everyone

When creating a room, choose Team walkthrough, Weekly check-in, or Design review. Each preset adds editable canvas prompts and a Session guide. Add expected names and customize the checklist before starting; choose Open canvas for a freeform room.

  1. Share the generated link and password separately. Approve your main window with Share a window; the first host window becomes featured automatically.
  2. Ask each teammate to join, choose their planned name or join as an additional participant, then choose Share a window or Watch & contribute and complete their checklist. The guide shows waiting names, participation, actual sharing status, and progress.
  3. Choose Feature beside a person or Next window to rotate through sharing teammates. Feature my window returns to your main presentation.

Each browser chooses Follow featured or Explore canvas independently. Following changes only that person's view, respects paused windows, and never starts capture. Each person still approves their own share in the browser picker. Planned names are self-selected labels, not verified accounts or an invitation restriction; joining still needs the room link and password.

Join from a phone or tablet

Open the same trusted HTTPS address on the team's network and join with the room link and password. A phone does not need its own Bun server. Choose Watch & contribute in the Session guide to complete your checklist without sharing a window; you can still chat, draw, write, and follow the presentation. Where capture is unavailable, Join without sharing makes this choice explicit.

Pinch with two fingers to zoom, or slide them to pan. One finger moves objects or draws with the selected tool. Select an object and use Edit to write. Focus enlarges an object locally and clears the mobile drawing controls; Back to canvas restores them. Pinching leaves Focus so you can explore.

Window capture and video recording depend on the browser's actual capabilities. The app explains unavailable capture without opening a picker; choosing a participation mode never starts or stops sharing. Keep the tab active for live collaboration, and download recordings before reloading or closing it. Check the native keyboard, source picker, and direct video connection on the devices your team uses.

Where the data lives

Standalone hosting, using new peer-canvas rooms
ContentLocation & lifetime
Room access, plan & chatThe host's data/rooms.json contains room metadata and names, guided-session plans and checklist state, password hashes, token hashes, and recent chat. Restrict access to that file. DATA_FILE can select another writable location.
Shared canvas & imagesNew rooms keep their Yjs canvas and embedded images in participants' browser memory and synchronize between peers. The host server stores no canvas snapshot. Export anything you want to keep before the last copy closes. The personal canvas saves on that browser's device.
Shared windowsVideo travels over WebRTC between peers, with TURN relaying only if configured. The application server does not store the video.
Recordings & snapshotsRecordings remain browser blobs until downloaded; reloading or closing the tab loses them. They are not synchronized. Choosing optional MP4 export sends selected media to the connected loopback worker on that same device, which removes its temporary files after the job. Downloads stay in the user's download location.
Optional diagnosticsLogging and telemetry export are off by default. Enabled diagnostics contain route categories, status, timing, and generated correlation IDs, excluding room IDs, request content, and credentials. An explicitly configured OTLP collector receives those redacted spans.

The standalone server's rooms have a default seven-day lifetime. Access tokens last 24 hours and are renewed when their browser reconnects. Explicitly leaving revokes that token; ending the room denies further access. Save needed exports and recordings before leaving.

Common's room creator is the host. This version has password-based rooms and open room creation for visitors who can reach it; it does not add enterprise SSO, administrator-only room creation, or host-account recovery. Use it on a trusted network appropriate to that access model.

Choose the network services you need

The local private profile runs without Cloudflare or Netlify services. Fonts and Mermaid are bundled. Installation and updates still need dependencies, and trusted HTTPS plus working browser-to-browser routes remain necessary for a shared session.

The launcher defaults to COMMON_NETWORK_PROFILE=private. Bare server starts and hosted deployments default to standard unless configured otherwise. Both serve their effective policy at /api/config, containing public settings and no TURN credentials.

  • STUN: private mode has no default STUN service. Set STUN_URLS to your organization's comma-separated URLs, or none to disable it explicitly. Standard mode defaults to Google and Cloudflare STUN; they receive connection metadata rather than relaying video.
  • Diagrams: private mode disables external PlantUML unless PLANTUML_URL selects a renderer; PLANTUML_URL=none disables it in either profile. Standard mode uses the consented public plantuml.com renderer. Rendering sends the complete source, and shared externalConsent can permit rendering on other participants' devices. Mermaid stays local.
  • Fonts: DM Sans is served from the installation. This guide uses system fonts and loads no external scripts or fonts.

Direct browser connections are the default, and a relay is not required to install or run Common. If a particular device cannot connect, use Connection details and check that device's actual network policy before changing infrastructure.

Optional advanced setting: an organization-operated relay

If your organization chooses a TURN relay, configure TURN_URLS plus TURN_SECRET, or dedicated TURN_USERNAME/TURN_CREDENTIAL, in the host environment. The server issues credentials only to admitted room participants. ICE_TRANSPORT_POLICY=relay forces relay routes and needs a working TURN setup; leave it as all for normal direct connections. Common does not operate a relay service.

One HTTPS endpoint gets people into the room; canvas and video also need working peer connections. Wi-Fi client isolation, VPN routing, NAT, or firewall policy can block them. Browser WASM does not bypass those boundaries. There is no fixed admission cap, but device memory, the full replicated canvas, host signaling work, and presenter upload still limit practical room size.

A larger video audience may need a separately operated SFU to forward one presenter's stream. Common does not include an SFU server or a ready-to-use SFU integration. A tunnel is optional too: choosing Cloudflare Tunnel routes tunneled HTTP/WebSocket traffic through Cloudflare and does not by itself relay WebRTC media. It is not part of the private local defaults.

An MP4, when you want one

Normal browser recording and downloads work without another process. For a compatible MP4, install FFmpeg with both ffmpeg and ffprobe available, then open a terminal on the same computer as the browser:

bun run media:export --origin http://localhost:3001

Use the app's actual origin, including its HTTPS port, instead of the localhost example when needed. On a teammate's computer, 127.0.0.1 means that teammate's own worker, not the room host. The worker listens on loopback, allows only the configured app origin, and prints a temporary session token.

  1. Open Canvas options → Recording exports.
  2. Enter the printed worker address and session token, then select Connect local worker. If your browser asks for local-network access, use its normal permission flow.
  3. Select a retained browser recording and choose Export recording as MP4, or choose PNG snapshots in playback order and Export image walkthrough.

The token stays in this tab and is not exposed through the agent API. Media is processed in temporary local files and deleted after the job. The original recording remains available. Closing the dialog cancels active work; Disconnect forgets the browser connection, and stopping the worker revokes its session token.

Exports are limited to five minutes, 100 MiB for a recording/output, and output up to 1920 × 1080. Image walkthroughs use 1–50 PNGs, up to 5 MiB each and 45 MiB combined in the picker, with 0.5–30 seconds per frame. They make a video from still frames rather than recording live browser interactions.

Use the optional Docker media engine

If you prefer a local container instead of a native FFmpeg installation, build its image and select that engine:

docker build -t common-media-ffmpeg:local media
bun run media:export --origin http://localhost:3001 --engine docker

This needs a working local Docker installation and compatible bind-mount paths. Each conversion runs with networking disabled and bounded container resources. Docker is optional and is not needed to run Common, share a window, or download the browser's original recording.

Check a session before the walkthrough

  1. Open the same trusted HTTPS address in two browser profiles or on two team devices. Create a password-protected room in the first and join its invite link in the second.
  2. Add a text note. Move, resize, reorder, and lock it from the two browsers; both should show the same result.
  3. Choose a window with the native share picker. Use Watch window on the other device and confirm live frames appear. Pause view should pause that video without stopping canvas edits.
  4. Send a chat message, then reload one participant while the other remains open. Confirm the participant reconnects, editing resumes, and the live canvas returns from its peer.
  5. Make a short recording, stop it, download it, and play the file. Download any export needed after the session before closing its last browser.

This checks your actual devices and network. A healthy server or a page that loads successfully does not by itself verify WebRTC, capture permissions, or recording codecs.

Open Canvas options → Connection details for ready/planned canvas connections, watched windows, queued bytes, configured relay status, and build information. Download connection report saves counts, states, and generated request IDs for correlation, without room identifiers, credentials, canvas content, or recordings.

For server investigation, /api/health checks the hosting adapter and /api/config shows its profile, transport, and build. Responses include X-Common-Request-Id for correlation. COMMON_LOG_DIAGNOSTICS=1 enables redacted logs; COMMON_OTLP_ENDPOINT can send bounded traces to an organization collector. Neither is enabled by default.

A few things to check

The page opens, but screen sharing is unavailable

Remote devices need a trusted https:// origin. Plain http://192.168… is not equivalent to localhost. Finish certificate trust, then check browser/operating-system capture permissions and choose the window with the native picker. An organization's browser policy may also restrict capture.

A colleague cannot open the invite link

Check that it uses the host's reachable LAN/VPN IP, not localhost. Keep the launcher running, prevent laptop sleep, and allow the team's access to TCP port 8443 in the host firewall. Run bun run doctor --https and confirm that devices can reach each other on the chosen LAN or VPN.

Rooms open, but the canvas or video never connects

HTTPS room admission can work while peer traffic is blocked. Use Connection details to inspect peer state, then check VPN routes, Wi-Fi client isolation, and peer/UDP firewall rules on the affected devices. For remote video, use Watch window on its tile; a paused view does not receive live frames.

The app uses the wrong transport or gets API errors

Open /api/config on the same origin. A local server should report transport: "websocket"; Netlify should report "polling". Confirm its profile and build identifier, restart after changing settings, and reload. Use bun run local for a fresh build if the assets predate runtime configuration. A proxy must serve this endpoint from the same server as the room API.

The optional export worker will not connect

Run it on the same computer as this browser, use the exact current app origin after --origin, and paste its current token. Check FFmpeg availability or your selected Docker engine. Browser local-network policy can still block a loopback connection; use the normal permissions or keep the original browser download instead. Do not disable browser protections to make export work.

The room rejects an origin or the WebSocket fails

Use the supplied Caddy reverse proxy with its host-preserving upstream, and have everyone use one common HTTPS origin. A replacement proxy must preserve Host and WebSocket upgrades. ALLOWED_ORIGINS can allow a deliberate additional origin; it does not repair a proxy that sends requests to the wrong server.

The host restarts, and a room or canvas looks different

Room metadata and recent chat use the host's data file, but new shared canvas content lives in browser memory. Keep a browser holding the live document or export what you need. Switching IP, protocol, or port also switches browser origin and its saved identity. An expired token requires joining again with the password.
